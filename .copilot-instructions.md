# Copilot Instructions - GQL Property Management System

## Project Overview

This is a GraphQL-based property/purchase management system built with:
- **Framework**: Strawberry GraphQL + FastAPI
- **Database**: PostgreSQL (two instances: postgres_gql for UG service, postgres_credentials for auth)
- **Authorization**: Role-Based Access Control (RBAC) with creator ownership
- **Deployment**: Docker Compose with 8 services
- **Federation**: Apollo Federation for distributed GraphQL architecture

### Key Components

#### 1. Authorization System (`src/GraphTypeDefinitions/authz_extensions.py`)
**CRITICAL**: This is the heart of the security system. It implements 3-tier authorization:

```python
# Authorization Checks (in order):
1. Creator Ownership - User owns the content (permanent)
2. Root Admin - Admin in root group (sees everything)
3. Group Role - Explicit role in entity's group or parent groups
```

**Key Functions:**
- `OwnershipPermissionExtension.resolve_async()` - Main authorization logic (lines ~240-350)
- `get_accessible_groups()` - Returns groups with roles + child groups (lines ~487-513)
- `get_group_children()` - Recursive child group lookup (lines ~416-465)
- `check_root_admin()` - Validates root admin status (lines ~467-485)
- `filter_by_permissions()` - Filters entity lists by permissions (lines ~597-665)

**Important Patterns:**
```python
# Hierarchical Access (ONE-WAY: parent → child, NOT child → parent)
accessible_groups = user_role_groups + child_groups_of_those_groups

# Root Admin Detection
admin_in_group_with_no_mastergroup = root_admin
```

#### 2. GraphQL Models (`src/GraphTypeDefinitions/`)
- `PurchaseGQLModel.py` - Purchase entities with RBAC (lines ~282-294: `purchase_page` resolver)
- `EventGQLModel.py` - Event management
- `UserGQLModel.py` - User federation (extended from gql_ug)
- `mutation.py` - All mutation operations
- `query.py` - Query aggregation

#### 3. Database Models (`src/DBDefinitions/`)
- `purchasemodel.py` - Purchase DB schema
- `EventDBModel.py` - Event DB schema
- `BaseModel.py` - Common base with `createdby_id`, `rbacobject_id`

#### 4. Main Entry Point (`main.py`)
- `get_context()` function (lines ~100-250) - Fetches user roles from UG service
- Authentication via Bearer token: `{"id": "uuid", "username": "email"}`
- Strawberry schema setup with extensions

## Authorization Flow

### For Any GraphQL Operation:

```
1. User makes request with Bearer token
   ↓
2. main.py:get_context() extracts user_id
   ↓
3. Query gql_ug service for user's roles
   ↓
4. OwnershipPermissionExtension.resolve_async() checks:
   - Is user the creator? → ALLOW
   - Is user root admin? → ALLOW ALL
   - Does user have required role in entity's group/parent? → ALLOW
   - Otherwise → DENY
```

### Hierarchical Access Rules:

```
University (Univerzita)
└── Faculty (Fakulta vojenské matematiky)
    └── Department (Katedra teoretické matematiky)

✅ University admin CAN access Faculty/Department content
❌ Department editor CANNOT access University content
✅ Creator ALWAYS accesses own content regardless of hierarchy
```

### Adding New Entities

1. **Create DB Model** (`src/DBDefinitions/`) with:
   - `id: UUID` (primary key)
   - `createdby_id: UUID` (for creator ownership)
   - `rbacobject_id: UUID` (for group permissions)

2. **Create GQL Model** (`src/GraphTypeDefinitions/`) with:
   - `@strawberry.federation.type(keys=["id"])`
   - Fields with `permission_classes=[OnlyForAuthentized]`

3. **Add Query/Mutation** using permission extensions:
   ```python
   @strawberry.field(permission_classes=[OnlyForAuthentized])
   async def my_entity_page(self, info, skip=0, limit=10):
       resolver = PageResolver[MyEntityGQLModel](whereType=MyEntityInputFilter)
       results = await resolver(self, info, skip=skip, limit=limit)
       return await filter_by_permissions(info, results, VIEWER_ROLES)
   ```

4. **Use Extension Factories**:
   ```python
   # For insert
   create_insert_permissions(InsertError[MyEntityGQLModel], MyEntityGQLModel, EDITOR_ROLES)
   
   # For update
   create_update_permissions(UpdateError[MyEntityGQLModel], MyEntityGQLModel, EDITOR_ROLES)
   
   # For delete
   create_delete_permissions(DeleteError[MyEntityGQLModel], MyEntityGQLModel, ADMIN_ROLES)
   ```

### Debugging Authorization Issues

1. **Check user roles**:
   ```graphql
   query { me { roles { roletype { name } group { id name mastergroupId } } } }
   ```

2. **Check entity's rbacobject_id**:
   ```graphql
   query { purchaseById(id: "uuid") { rbacobjectId createdby { id } } }
   ```

3. **Verify group hierarchy**:
   ```graphql
   query { groupById(id: "uuid") { name mastergroupId subgroups { id name } } }
   ```

4. **Common issues**:
   - Empty roles array → Check gql_ug Docker volume mount
   - User can't access own content → Check `createdby_id` matches user `id`
   - Hierarchical access wrong → Check `mastergroupId` chain
   - Child seeing parent content → BUG (should never happen)

## Development Guidelines

### DO's:
✅ Always use `filter_by_permissions()` for entity lists
✅ Include `rbacobject_id` in all RBAC-protected entities
✅ Set `createdby_id` automatically from `info.context['user']['id']`
✅ Test with multiple users at different hierarchy levels
✅ Use extension factories for consistent permission checks
✅ Verify parent→child access works, child→parent blocked

### DON'Ts:
❌ Never bypass authorization extensions
❌ Don't add implicit access without explicit roles (security risk)
❌ Don't forget to mount systemdata.rnd.json in Docker
❌ Don't use group membership without role verification
❌ Never allow child groups to access parent group content
❌ Don't hardcode user IDs in queries

## Security Principles

1. **Creator Ownership is Sacred** - Users never lose access to their own content
2. **Explicit Roles Required** - No implicit access based on group membership alone
3. **Hierarchy is One-Way** - Parents access children, NOT vice versa
4. **Root Admin Exception** - Only admins in groups with `mastergroupId=NULL`
5. **Defense in Depth** - Authorization at resolver level + entity filtering

## Common Pitfalls

### 1. Empty Roles Array
**Symptom**: Query returns `me.roles = []`
**Cause**: gql_ug service not loading systemdata.rnd.json
**Fix**: Check Docker volume mount in docker-compose.debug.yml line 120-121

### 2. Hierarchical Access Violation
**Symptom**: Child department user sees parent department content
**Cause**: Incorrect parent group lookup or implicit membership logic
**Fix**: Ensure `get_accessible_groups()` only adds CHILDREN, not parents

### 3. Creator Can't Access Own Content
**Symptom**: 403 error on own purchases
**Cause**: `createdby_id` not set or doesn't match user ID
**Fix**: Verify `createdby_id` in database matches `info.context['user']['id']`

### 4. Permission Extension Order Matters
**Wrong**:
```python
[LoadDataExtension, OwnershipPermissionExtension]  # ❌ No data loaded yet!
```

**Correct**:
```python
[OwnershipPermissionExtension, LoadDataExtension]  # ✅ Check first, load after
```

## When Modifying Authorization

⚠️ **EXTREME CAUTION REQUIRED** ⚠️

The authorization system is security-critical. Any changes must:

1. **Maintain Security Boundaries**
   - Never allow child→parent access
   - Never grant access without verification
   - Always require explicit roles for group access

2. **Test Thoroughly**
   - Test with root admin (should see all)
   - Test with creator (should see own)
   - Test with role in correct group (should see group content)
   - Test with role in wrong group (should be denied)
   - Test with no roles (should be denied unless creator)
   - Test hierarchical access (parent→child ✅, child→parent ❌)

3. **Document Changes**
   - Update CREATOR_OWNERSHIP_GUIDE.md
   - Update this file
   - Add comments in authz_extensions.py
